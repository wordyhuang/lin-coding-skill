# 阶段 2 · 三层递进调研（规程）

> 输入：阶段 1 的《需求确认单》（全部 READY）。产出：《技术方案调研报告》。人设延续资深需求分析师——**调研是主动行为，用户未要求也执行**；每条结论必须带出处。

## 1. 三层递进（按序执行，上层能解决的不下沉）

### 第 ① 层 · 林枢宿主服务（能不造的轮子不造）

1. 读取宿主服务契约（15 项）：Gitee raw
   `https://gitee.com/wordy_huang/linhub/raw/master/code/host/linhub/host/src/services/services.php`
2. 读取平台服务接入指引与各服务契约文档：
   `https://gitee.com/wordy_huang/linhub/raw/master/coding-guide/08_平台服务接入指引.md`
   及 `coding-guide/services/` 下相关契约（请求需跟随重定向）。
3. 将需求确认单中的每类能力诉求对照宿主服务清单，逐项给三态结论：
   - ✅ 宿主已提供 → 记服务 id 与接入方式（注入 / 订阅 topic / 工作台插槽 / ui_replace）
   - ⚠️ 部分提供 → 写明差距与适配方式
   - ❌ 不提供 → 进入第 ② 层调研

### 第 ② 层 · 开源社区现成方案（❌ 项逐个调研）

1. 对第 ① 层判 ❌ 的能力，搜索开源社区现成轮子（WebSearch / GitHub 检索）。
2. **前端类能力先查 workdesktop-ai 是否已覆盖**（再往社区找轮子）：按其 AI 阅读路由 `https://gitee.com/wordy_huang/workdesktop-ai/raw/main/ai-router.md`（场景判定速查表）→ `scenarios/0N-*.md`（场景）与 `ai-api/`（34 组件精确 API，GitHub 镜像 `https://github.com/wordyhuang/workdesktop-ai`）；已覆盖即记 ✅（附组件名 + `ai-api/wd-{组件名kebab}.md` 出处），**禁止凭记忆判断组件能力**。
3. 每个候选记录：项目名、链接、活跃度（最近提交/issue）、许可证、与林枢技术栈（PHP 8 + ThinkPHP 8 + MySQL + Vue3 UMD）的兼容性。
4. 逐项三态结论：✅ 直接复用（附接入方式）/ ⚠️ 参考实现（附借鉴点）/ ❌ 仍需自建（附理由）。
5. 注意：**林枢功能包禁止引入 npm 构建链（SOP F-12）**，前端类轮子必须以 UMD 直引或纯后端实现为前提评估。

### 第 ③ 层 · 大厂同类产品架构参考

1. 调研 2~3 个同类成熟产品（大厂开源或公开架构）的对应模块设计。
2. 只提炼**架构思路与功能拆分方式**供方案设计参考，标注来源链接；不照抄与其技术栈绑定的实现。

## 2. 技术方案调研报告（产出物）

结构：

1. **三层结论汇总表**：能力 × 层级 × 三态结论 × 出处。
2. **候选方案（≤3 个）**：每个方案含架构概述、复用清单、风险、工作量直觉评估。
3. **推荐方案** + 每个未选中方案的放弃理由。
4. **框架确认素材**：按 SOP §8.1 决策流程给出推荐框架（A/B/C），列出判断依据。

## 3. 同轮完成的两项 SOP 强制前置确认

按 SOP §8.6.1 提问模板，一次性向用户确认（不连环追问）：

1. **框架确认（A/B/C）**：A · 林枢功能包（推荐，理由见 SOP §8.1 默认推荐）/ B · 自主构建（B1 同款前端 / B2 工程化 SPA）/ C · 其他宿主。未获用户确认禁止创建任何产物。
2. **{SHORT} 名称确认**：项目英文短名（如 `lin-crm`），用作输出文件夹名与 doc_id 短名。分析师可给建议值，但**未获用户确认禁止创建任何产物**；用户给不出时必须请用户提供，禁止自行命名。

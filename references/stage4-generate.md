# 阶段 4 · 开工包生成 + 生成后审计闭环（规程）

> 前置：G0~G3 全过（需求确认单 READY、调研报告定稿、框架与 {SHORT} 已确认、生成前审计通过）。本阶段严格按内嵌 SOP 执行——**本文件只写编排与门禁，规则细节一律以 `sop-v1.8.md` 为准**。

2. {SHORT} 已获用户确认（值记录在案）→ 否则**必须询问用户**，禁止占位创建。
3. **解析输出根目录**（按 SKILL.md §4 优先级）：agent 任务目录存在 → `{任务目录}/dist/`；用户显式指定 → 用户目录；否则**询问用户确定**，禁止静默落盘。输出文件夹 = `{输出根目录}/{SHORT}/`。解析结果向用户播报一句确认。

## 2. 执行编排（严格串行，禁止乱序、禁止跳项）

1. **读 SOP**：完整读取 `sop-v1.8.md` §1~§8 + 附录 A（禁止只读标题开工）。
2. **门禁 A · 通用事实源前置（硬性门禁，先于一切文件产出）**：
   - 凡涉及**声明文件**（`manifest.php` / `menus.php` / `permissions.php` / `route.php` / `shortcuts.php` / `workspace.php`）或**页面文件**（`src/view/**`）的产出，动手前**必须通读 coding-guide 对应章节全文**——含版本变化记录中后期新增的小节（如 guide04 §6.2「宿主渲染规则与 group 聚合分组」、§7.2「包页面 GUI 渲染规范」），**禁止只读开头示例或凭记忆、惯性书写**；
   - **设计菜单前先执行 guide04 §6.2「菜单归类指导」第 1 条强制前置**：先查宿主 `workspaces.php` 六分导台定义 + 已装包 `menus.php`（快照见 `registry.json`），确认目标分导台下**已有一级菜单与已用 `group` 值**，再定 `parent`；按原生 **group 聚合模式**实现（同 group 值的一级菜单聚合到同一标题分组，父节点挂 `children` 后 `perms` 填子项权限码并集），**禁止自创折叠/嵌套中间层**；
   - **被用户纠偏后，第一步永远是回查事实源**（coding-guide 对应章节 + 宿主源码 + 已装包实例），确认规范后再改，**禁止直接给新方案**。
3. **门禁 B · 前端 UMD 范式（页面文件专用）**：凡涉及 `src/view/` 下任何页面文件的产出，**必须先完整阅读** `coding-guide/03_前端编码指引.md` §三（页面骨架）与 `coding-guide/04_功能包开发指引.md` §7.2（包页面 GUI 渲染规范——"唯一正确模式"，读取方式见 `stage3-audit.md` §0 事实源表），**禁止凭记忆或惯性书写页面骨架**。页面骨架唯一合法形态（**缺一即返工**）：
   - **双 CSS**：`element-plus/index.css` + `workdesktop-ai/style.css` 各 1 条 `<link>`；
   - **四个 UMD `<script src>` 直引**（加载顺序固定）：vue → element-plus → icons → workdesktop-ai；
   - **`<script type="text/x-template" id="xxx-tpl">`** 承载页面模板（字符串模板，规避 in-DOM 解析缺陷）；
   - **`createApp({ template: '#xxx-tpl' })`**，且必须 `app.use(ElementPlus)` 与 `app.use(WorkDesktop)`；
   - **数据请求一律走 `WD.request`**：成功判定 `code >= 0`，失败码必须为负数，解封字段为 `code / message / data`。

   **明确禁止项**：in-DOM 模板挂载（`app.mount` 读内联 DOM——`el-form` 之后会静默截断且无报错）、裸 `fetch`/`axios` 自行封装、npm 构建链。
4. **TASK-00~TASK-17**：按附录 A 任务清单逐项串行执行（SOP §3 生成顺序：⓪ 框架与名称确认 → ① 需求清单 → ②③④ DB/后端/前端清单 → ⑤ 任务对账单 → ⑥ 对接点位清单）。
5. **源 PRD 替代**：本流程的"源 PRD" = 阶段 1《需求确认单》+ 阶段 2《技术方案调研报告》。红线 1（唯一事实来源、禁止凭印象补全）同样适用；发现两者冲突 → 以确认单为准并登记 OI。
6. **林枢资料读取**：SOP 中林枢资料引用已直接写为社区仓库地址（Gitee raw 主源 + GitHub 镜像），照其读取；framework=linshu 时 TASK-12 前必须先读 `08_平台服务接入指引.md`、`services/` 契约与 `services.php`。
7. **TASK-CHECKLIST 即时标记**：每完成一项 TASK 立即更新副本状态（SOP §6），禁止批量补标。
8. **红线**：SOP §4 六条红线全程生效（五类副本跨文件一致、框架口径三处一致、OI 阻塞继承等）。

## 3. 生成后审计闭环（门禁 G4b）

六份文件全部落盘后、收尾任务前，执行两段审计（规程见 `stage3-audit.md` post-gen 模式）：

1. **SOP 六维审计 A1~A6**（SOP §5，结论写 TASK-CHECKLIST A.2 审计记录区）。
2. **skill 规范审计 C1~C9**（对照 Gitee raw coding-guide + services.php + workdesktop-ai，含页面 UMD 范式机器扫描与菜单结构符合性核对）。

闭环规则：

- 任一维/项不通过 → **直接用编辑工具修改文档正文**（不输出审计日志文件）→ 复审 → 循环至全部通过。
- 对话中仅汇报"发现 X 处、已修正"级别摘要。
- 全部通过后继续收尾 TASK（TASK-14~17），全部 TASK done 方可宣布交付。

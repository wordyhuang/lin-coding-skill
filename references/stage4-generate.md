# 阶段 4 · 开工包生成 + 生成后审计闭环（规程）

> 前置：G0~G3 全过（需求确认单 READY、调研报告定稿、框架与 {SHORT} 已确认、生成前审计通过）。本阶段严格按内嵌 SOP 执行——**本文件只写编排与门禁，规则细节一律以 `sop-v1.8.md` 为准**。

## 0. 启动自检（每次进入本阶段执行）

1. `references/sop-v1.8.md` 存在且头部 `doc_id: SOP-KICKOFF-V1_8` → 否则阻塞。
2. {SHORT} 已获用户确认（值记录在案）→ 否则**必须询问用户**，禁止占位创建。
3. **解析输出根目录**（按 SKILL.md §4 优先级）：agent 任务目录存在 → `{任务目录}/dist/`；用户显式指定 → 用户目录；否则**询问用户确定**，禁止静默落盘。输出文件夹 = `{输出根目录}/{SHORT}/`。解析结果向用户播报一句确认。

## 1. 命名门禁 G4a（创建任何产物前）

| 产物 | 命名规则（出处：SOP §1/§2.1 + SKILL.md §4 输出目录覆盖） |
|---|---|
| 输出根目录 | 优先级：`{任务目录}/dist/`（agent 任务上下文，首选）→ 用户指定目录 → 询问用户确定；输出文件夹 = `{输出根目录}/{SHORT}/`（两级结构，根目录不含 {SHORT}），已存在则直接使用，禁止重建或清空 |
| 六份文件名 | 不带任何前缀：`产品需求清单_v1.0.md`、`数据库开发任务清单_v1.0.md`、`后端开发任务清单_v1.0.md`、`前端开发任务清单_v1.0.md`、`完整任务对账单_v1.0.md`、`上下游对接点位清单_v1.0.md` |
| 任务清单副本 | `{SHORT}\TASK-CHECKLIST.md` |
| doc_id 短名 | `{SHORT}` 大写 |

**名称不明确（{SHORT} 未确认、文件版本号有歧义等）→ 停下问用户，禁止自行命名、禁止占位符产物。**

## 2. 执行编排（严格串行，禁止乱序、禁止跳项）

1. **读 SOP**：完整读取 `sop-v1.8.md` §1~§8 + 附录 A（禁止只读标题开工）。
2. **TASK-00~TASK-17**：按附录 A 任务清单逐项串行执行（SOP §3 生成顺序：⓪ 框架与名称确认 → ① 需求清单 → ②③④ DB/后端/前端清单 → ⑤ 任务对账单 → ⑥ 对接点位清单）。
3. **源 PRD 替代**：本流程的"源 PRD" = 阶段 1《需求确认单》+ 阶段 2《技术方案调研报告》。红线 1（唯一事实来源、禁止凭印象补全）同样适用；发现两者冲突 → 以确认单为准并登记 OI。
4. **林枢资料读取**：SOP 中林枢资料引用已直接写为社区仓库地址（Gitee raw 主源 + GitHub 镜像），照其读取；framework=linshu 时 TASK-12 前必须先读 `08_平台服务接入指引.md`、`services/` 契约与 `services.php`。
5. **TASK-CHECKLIST 即时标记**：每完成一项 TASK 立即更新副本状态（SOP §6），禁止批量补标。
6. **红线**：SOP §4 六条红线全程生效（五类副本跨文件一致、框架口径三处一致、OI 阻塞继承等）。

## 3. 生成后审计闭环（门禁 G4b）

六份文件全部落盘后、收尾任务前，执行两段审计（规程见 `stage3-audit.md` post-gen 模式）：

1. **SOP 六维审计 A1~A6**（SOP §5，结论写 TASK-CHECKLIST A.2 审计记录区）。
2. **skill 规范审计 C1~C5**（对照 Gitee raw coding-guide + services.php + workdesktop-ai）。

闭环规则：

- 任一维/项不通过 → **直接用编辑工具修改文档正文**（不输出审计日志文件）→ 复审 → 循环至全部通过。
- 对话中仅汇报"发现 X 处、已修正"级别摘要。
- 全部通过后继续收尾 TASK（TASK-14~17），全部 TASK done 方可宣布交付。

## 4. 交付

交付物：`{SHORT}\` 下六份文件 + `TASK-CHECKLIST.md`，外加流程级产物《需求确认单》《技术方案调研报告》。交付时向用户汇报：产出文件清单 + 双重审计结论摘要（六维全过、规范审计 C1~C5 全过）。

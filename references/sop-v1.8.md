# 开工包生成 SOP（统一版）

> 本文件是唯一可执行 SOP，**项目无关**（不绑定"林工"或任何前缀，适用于任意项目）。
> 触发词：用户提供源 PRD 路径并要求"生成开工包"。
> **执行规程：必须先完整读完本文件 §1~§8 全部内容，再用附录 A 开工。禁止只读标题即开工。**
> 原三份配套文件（生成指导 / 框架选型说明 / 任务清单模板）已整合进本文件，引用一律指向本文内章节，不存在外部依赖。

## 1. 输入与准备

| 项 | 规则 |
|----|------|
| 输入 | 源 PRD 绝对路径（唯一事实来源） |
| 前置校验 | 文件不存在 / 不可读 → 立即停止，输出阻塞报告，不做任何产出 |
| **名称确认（强制前置，先于一切产物）** | **创建任何文件夹或文件之前，必须向用户确认一项名称：项目英文短名 `{SHORT}`（如 `lin-crm`），同时用作输出文件夹名与 doc_id 短名，不再需要项目中文名 / 文件名前缀。** AI 可从源 PRD / 源目录推导建议值（如 `lin-trade`、`lin-crm`）供用户确认或修改，但**未获用户确认前禁止创建任何产物** |
| **框架确认（强制前置，与名称确认同级）** | **必须向用户确认本项目采用哪种技术框架：① 基于林枢功能包；② 自主构建；③ 其他框架 / 客户既有宿主。** AI 必须先完整读本文件 §8（框架选型说明），再用 §8.6.1 提问模板一次性问清，**提问须附三方案一句话说明与推荐项（默认推荐 A · 林枢）**；未获确认前禁止创建任何产物。框架决定三件事：**前端构建口径、接入声明章节、后端 T0 基建范围**——选 A 时前端固定 **workdesktop-ai + 林枢前端构建意见 12 条（§8.2.4 的 F-01~F-12）**；选 B 时须同轮确定 B1（同款前端自建宿主能力）/ B2（Vite 工程化 SPA）并写明构建方式；选 C 时须先取齐宿主资料 8 项（§8.4.2），未齐不得产出文件 2~5。**框架同时决定文件 6 的服务映射口径**（林枢=宿主服务映射 / 自建=自建能力映射 / 其他=宿主能力映射，见 §2.4 文件 6） |
| `{SHORT}` | 用户确认的项目英文短名（如 `lin-crm`、`lin-trade`，或用户指定的任意英文名），是**唯一名称参数**：输出文件夹 = `{输出根目录}/{SHORT}/`；doc_id 短名 = `{SHORT}` 大写（如 `lin-crm` → `LIN-CRM`）；六份文件名**不带任何前缀**（项目身份由文件夹承载） |
| 输出根目录 | 按优先级解析一次并全程使用：① agent 任务目录存在 → `{任务目录}/dist/`；② 用户显式指定 → 用户指定目录；③ 均无 → 询问用户确定，禁止静默落盘。输出文件夹 = `{输出根目录}/{SHORT}/`；已存在则直接使用，禁止重建或清空 |

### 2.3 六份文件的公共要求（每一份都必须满足）

1. **YAML front matter**（文件第一行开始）：

```yaml
---
doc_id: {上表 doc_id}
consumer: ai_agent
source_of_truth: "{源 PRD 绝对路径}"
reading_protocol: A8
coding_guide: linhub/coding-guide   # 全部输出文档必填（见公共要求 7）
framework: {linshu | self_built | other:<宿主名>}   # 用户确认结果，取值见 §8.6.3
frontend_build: {workdesktop-ai | workdesktop-ai-self-hosted | vite-spa | react-spa | host-container | host-plugin}
blockers: [OI 编号列表]        # 无则 []
fr_total: N                    # 需求清单必填；任务清单用 task_total: N
---
```

2. 任务类清单额外必填：`hard_blockers` / `conditional_blockers`（任务级映射）；后端清单另加 `m1_scope` / `m2_scope`；对账单（文件 5）加 `usage: master_reconciliation`（汇总 + 完成情况对账监控）；对接点位清单（文件 6）加 `usage: integration_register` 与 `point_total: N`（预留对接登记，`blockers` 登记对接对象未定稿项）。
3. 文末脚注行：`*V_x.x · 日期 · 任务/FR 数 · 人日估算 · 阻塞项*`。
4. 歧义词黑名单：全文禁止出现"等 / 酌情 / 原则上 / 尽量 / 适当 / 相关"（引用源 PRD 原文除外）。
5. 所有编号引用格式：`FR-{模块}-{序号}`、`ENT`（实体）、`EVT`（事件）、`CFG`（配置）、`STM`（状态机）、`PG-{模块}-{序号}`（页面）、`OI-{字母}{序号}`、任务 ID（DB-xx / T组-xx / FE-xx / PM-xx / QA-xx / REL-xx）。
6. **框架基线（强制）**：六份文件 front matter 必须声明 `framework` 与 `frontend_build`，取值与用户在 §1 的确认结果一致；文件 4 必须展开 §0.2 前端技术基线。**front matter ↔ 文件 4 §0.2 ↔ TASK-CHECKLIST 汇总区三处必须一致**，不一致即框架漂移（见 §5 A5）。禁止跨框架混写：声明 `linshu` 却在文件 4 出现 Vite 脚手架任务、或声明 `self_built` 却保留 manifest / `permissions.php` 等林枢专属产出，均判不通过。
7. **编码规范遵循声明（强制，无条件适用于所有框架）**：所有输出文档——六份文件 + `TASK-CHECKLIST.md`——必须在 §0 元信息区（TASK-CHECKLIST 为文档头部）包含以下固定声明，逐字一致、缺一即必含项不齐：
   > **编码规范**：本项目所有编码（后端 / 前端 / 数据库 / 迁移 / 脚本）均须遵循 **linhub 编码规范（coding-guide 00~08）**。规范事实源：Gitee `https://gitee.com/wordy_huang/linhub`（主源，master 分支）/ GitHub `https://github.com/wordyhuang/linhub`（镜像）。各指引文档：00 总纲 / 01 需求与协作 / 02 后端 / 03 前端 / 04 功能包开发 / 05 数据与迁移 / 06 事件与集成 / 07 安全与合规 / 08 平台服务接入（以仓库实际目录为准）。
   - front matter 同步声明 `coding_guide: linhub/coding-guide`；
   - 各文件 §0.1 AI 会话规约 / 提示词模板中必须含对应提醒："开工前阅读 coding-guide 对应指引，实现遵循其条目；与本文冲突时登记 OI，不得静默偏离"；
   - 该声明不随框架变化——即使 `self_built` / `other` 框架，编码仍须遵循 linhub coding-guide。

## 4. 红线（优先级高于一切默认行为）

1. **源 PRD 是唯一事实来源**：逐行精确提取，禁止凭印象补全；提取数据与源文冲突时以源文为准并输出漂移报告。
2. **不修改源 PRD**。发现的问题一律登记为 OI，固定检查单（逐项核对，命中即登记）：
   - 表前缀 {SHORT} 段与项目短名不一致，或连字符被替换为下划线（如 PRD 写 `lg_lin_crm_`）→ 登记修正 OI（规范要求 `{SHORT}` 原样完整保留，如 `lg_lin-crm_`）；
   - 配置计数漂移（§配置表 vs 正文引用键不一致）→ 合并全量登记；
   - 无 FR 编号 / 无 AC → 本清单建映射，PRD v1.2 回填；
   - 状态机缺审批承载（配置能开审批流但无对应状态）；
   - 业务转化双路径（两事件均可触发同一结果）→ 幂等/主链路 OI；
   - 实体缺口（有编码/事件/功能但无落表）→ 显式登记缺口表；
   - 菜单清单未展开；
   - 状态枚举不统一（中英混用 / 同义不同名）。
3. **五类副本跨文件一致**：实体数 / 事件数 / 配置数 / 权限数 / 状态机枚举五类数据在六份文件中数值与内容必须一致；对接点位清单（文件 6）中"本期已实现"点位引用的事件与对外服务，必须与文件 1 附录 C、接入声明一致，不得另造第三套口径。不一致 = 漂移，修正后再交付。
4. **全部任务挂 FR 编号 + 可测 DoD**；后端覆盖矩阵 100%；OI 阻塞继承到任务级（⛔ 标记）。
5. **每写完一份文件，立即更新任务清单**（规约见 §6），禁止批量补标。
6. **框架口径不得默认、不得混写**：框架属于用户决策项，AI 不得以"PRD 里有 manifest 就是林枢"为由跳过确认（PRD 有接入声明只作为推荐依据，仍须用户点头）。确认结果必须落到三处并保持一致：六份 front matter 的 `framework` / `frontend_build`、文件 4 §0.2 前端技术基线、TASK-CHECKLIST §3 汇总区（附录 A.3）。选林枢时前端一律 workdesktop-ai + F-01~F-12，**禁止私自改用 Vite/webpack 等构建链**；选非林枢时必须在文件 4 写明前端构建方式，不得留空。

## 6. 任务清单使用规约（模板见附录 A）

1. **运行开始**：复制本文件附录 A → `{SHORT}/TASK-CHECKLIST.md`（本次运行的任务清单实例），此后标记动作发生在副本上；SOP 正文的附录 A 保持只读，禁止在 SOP 上标记。**附录 A 只承载进度状态，不承载规则细节**——副本与 SOP 正文配套使用，避免规则双副本漂移。
2. **即时标记**：每完成一项 TASK，立即用编辑工具更新该行：`状态 pending → done`、填入完成时间（真实系统时间）、备注填产出文件名或关键发现。
3. **禁止**：批量补标；未完成标 done；跳项执行。
4. **异常标记**：任务失败 → `failed` + 失败原因；被 OI 阻塞 → `blocked` + OI 编号。
5. 全部 TASK done 后，开工包方可视为交付完成。

## 7. 任务对账回写规约（开发期，AI 必须执行）

任务对账单（文件 5）的**任务对账总表是开发期唯一完成情况监控事实**。开工包交付后进入开发阶段时：

1. **回写时机**：AI 每开始一项任务、完成一项任务（子清单 DoD 全过）、或任务被 OI 阻塞时，**立即**回写对账总表对应行，禁止批量补写、禁止跨任务累积后一次更新。
2. **对账三要素**：每次回写必须保持"承诺 ↔ 实际 ↔ 证据"三要素齐备——承诺 = 子清单 DoD（引用编号或摘要）；实际 = 当前状态；证据 = DoD 逐条通过记录 / 产出文件 / 自测结果。
3. **证据红线（监控的核心）**：状态标 `已完成` 时**必须同步填入完成证据**（产出文件清单 + DoD 通过记录或收尾汇报摘录）；**无证据禁止标"已完成"**；DoD 有部分未达 → 标 `偏离` + 差异备注，禁止按"已完成"对账。
4. **状态取值**：`待启动` → `进行中`（开工时）→ `已完成`（DoD 全过 + 证据齐备）/ `偏离`（DoD 部分未达，注明差异与去向）/ `BLOCKED`（标 OI 编号）。
5. **三处一致**：对账总表状态 ↔ 子清单任务行状态 ↔ front matter blockers，发现不同步先修正再继续。
6. **事实来源分工**：任务"做什么、DoD 是什么"看子清单任务行；任务"做到哪了、完成得怎么样"看任务对账单对账总表。子清单是明细事实来源，对账总表是完成情况监控事实来源。
7. **对账小结**：每个里程碑波次收尾时，在该波次行附对账小结（应完成数 / 实际完成数 / 差异项及去向），供排期调整与评审引用。

### 8.1 三选一决策流程

```
源 PRD 是否声明接入某宿主（manifest / 权限声明 / 菜单声明 / 平台版本约束）？
├── 是，且宿主为林枢 ─────────────→ 方案 A · 林枢功能包（前端固定 workdesktop-ai）
├── 是，但宿主为其他平台 ─────────→ 方案 C · 其他框架 / 客户既有宿主（前端按宿主规范）
└── 否 / PRD 未涉及技术形态 ──────→ 问用户：交付形态是「并入林工矩阵」还是「独立售卖的单体应用」？
     ├── 并入林工矩阵 ──────────→ 方案 A · 林枢功能包
     ├── 独立售卖、不接宿主 ────→ 方案 B · 自主构建
     └── 已有系统上扩展 ────────→ 方案 C · 其他框架 / 客户既有宿主
```

**默认推荐：方案 A。** 理由：林工矩阵八款产品（林销 / 林客 / 林艺 / 林仓 / 林账 / 林员 / 林备 / 林质）共用一套宿主，权限、菜单、事件总线、迁移引擎由宿主提供，功能包只写业务；选 A 时后端基建任务可少 20~30%，且天然支持"独立可卖、组合成拳"。

### 8.2 方案 A · 林枢功能包（推荐）

#### 8.2.1 平台定位

林工·基础平台（代号**林枢 / linhub**）是功能包宿主。功能包与宿主**同进程代码级加载**，通过 manifest 声明式接入，不在包内重复实现 RBAC、菜单、事件总线与迁移引擎。

#### 8.2.2 技术栈（宿主给定，功能包不得偏离）

| 层 | 选型 | 版本 | 约束 |
|---|---|---|---|
| 语言 | PHP | 8.0+（协议校验写 8.1，见 §8.2.6 待确认） | 包内不得引入其他运行时 |
| 后端框架 | ThinkPHP | 8.x | 多模块架构，接口走模块化路由 |
| 前端组件库 | **workdesktop-ai** | 1.x | Vue 3 + Element Plus 企业级组件库，**UMD 直引，无构建** |
| 前端框架 | Vue | 3.x | UMD 方式与 workdesktop-ai 一同加载 |
| 渲染模式 | 静态页面 · 标准 API 驱动 | — | 前端为静态页面，**不使用模板标签**；数据一律通过统一 request 请求后端标准 API；后端负责输出标准 API |
| API 响应格式 | 统一 `{code, data, message}` | — | **后端必须适配 workdesktop-ai 的成功判定：`code >= successCode(0)`——即 0 与正数均判成功**（0 = 默认成功；正数可承载业务成功语义，如部分成功 / 提示级返回）；**失败一律使用负数 code**（错误码取负数区间，message 给可读原因）；**禁止用正数或 0 表示失败**，否则前端会误判为成功 |

| 缓存 / 队列 | Redis / Redis Stream | 5.x+ | 缓存、会话、轻量事件总线 |
| Web 服务 | Nginx / Apache + PHP-FPM | — | — |

#### 8.2.4 前端构建口径（林枢前端构建意见，12 条硬性合规项）

选林枢时，文件 4 必须逐条对齐下表；**任一条不符即为违规**，不得以"更好实现"为由偏离。

| # | 合规项 | 具体要求 | 检查方式 |
|---|---|---|---|
| F-01 | 渲染模式 | 前端为静态页面，**不使用模板标签**（不依赖 ThinkPHP View 模板输出页面数据）；数据一律通过统一 request 请求后端标准 API，后端负责输出标准 API；**不做全量 SPA 接管** | 文件 4 §0.2 声明渲染模式 |
| F-02 | 资源引入 | 公共布局 head 统一引入 element-plus css → workdesktop-ai css → vue3 UMD → element-plus UMD → workdesktop-ai UMD；**禁止私有版本、禁止多版本共存** | 文件 4 §0.2 + FE-00 DoD |
| F-03 | 应用创建 | 统一 `createReadyApp({...}).mount()`；不得自行 `createApp` 拼装或绕开框架初始化 | 组件与页面任务 DoD |
| F-04 | 组件优先 | 优先 `wd-station` / `wd-data-grid` / `wd-data-form` / `wd-search-panel` / `wd-drawer` / `wd-viewer` / `wd-button` / `editable-grid` / `wd-descriptions`；**不得自造同类组件** | 文件 4 §0.2 组件映射表 |
| F-05 | 首屏数据 | 首屏数据**同样通过统一 request 请求标准 API 获取**；**禁止服务端模板注入数据**（不再使用 `window.__INITIAL_DATA__` 等服务端注入方式） | FE-00 + 各页面 DoD |
| F-06 | 请求层 | 统一 `window.workDesktopConfig.request`（baseURL `/api`、拦截器注入 `uais_token`）；页面内禁止裸 `fetch`/`axios.create`；**成功判定遵循 WD 约定 `code >= successCode(0)`（0 与正数均成功），失败由后端负数 code 表达——前端不得自行改写 successCode 判定逻辑** | 文件 4 §4 接口表 |
| F-07 | 路由与菜单 | 菜单树来自 `menus.php`，**前端不自建菜单**；页面路由落在本包 view 目录，挂到宿主导航 | FE-00 DoD |
| F-08 | 权限控制 | 前端只控显隐与置灰，服务端二次校验；权限码取自 `permissions.php`，禁止自造 | FE-04 DoD |
| F-09 | 跨组件联动 | 用框架的 Headquarters 通信中心；**不自造事件总线** | 组件任务 DoD |
| F-10 | 主题 | 统一宿主主题色与风格，**不自造皮肤** | 页面任务 DoD |
| F-11 | 静态资源 | 落在 `public/lgg/<short>/`，不写公共目录 | 文件 4 §0.2 + 部署说明 |
| F-12 | 无构建链 | **不引入 Vite / webpack / npm 打包**；组件与工具以 UMD 直引 | 文件 4 任务表不得出现脚手架 / 构建产物任务 |

> 上述 12 条落到任务上：FE-00（工程初始化）承载 F-01/F-02/F-03/F-07，FE-01（通用组件库）承载 F-04，FE-04 承载 F-08，FE-90/FE-91（联调）承载 F-05/F-06，其余为页面级 DoD 检查项。

**允许的偏离（须登记 OI）**：仅当宿主版本不支持某项（如 F-01 需嵌独立 SPA 子系统）时，须在文件 1 §2 登记 OI，写明偏离项、原因、宿主确认人与回退方案；**不得静默偏离**。

#### 8.2.6 前置条件与风险（选 A 前必须核对）

| # | 项 | 说明 | 处置 |
|---|---|---|---|
| 1 | 宿主版本 | `platform.host` 需给出可行约束（如 `>=1.0,<2.0`） | 未给出则在文件 1 §2 登记 OI |
| 2 | **表前缀短名不一致** | 规范要求 `lg_{SHORT}_<表名>`，`{SHORT}` 原样完整保留（含连字符，如 `lg_lin-crm_`）；若 PRD 写 `lg_lin_crm_`（连字符被替换为下划线）或缺段，则与规范不一致 | 登记修正 OI；SQL 中表名一律用反引号包裹（规避连字符转义问题），**不作为阻塞** |
| 3 | PHP 版本口径不一 | 协议规范 `platform.php` 示例写 `>=8.1`，统一架构规范写 `8.0+` | 登记 OI 由宿主负责人定稿，避免安装校验误拒 |
| 4 | MySQL 5.5 限制 | 5.5 无 CTE / 窗口函数 / JSON 类型 / 生成列 / `utf8mb4_0900` 排序规则 | 文件 2 硬规则写明禁用项，索引长度按 767 字节核算 |

| 6 | 界面替换与工作台插槽 | 仅当需要替换宿主页面或提供工作台卡片时才产出，避免无谓耦合 | 未涉及则在接入声明中写"无" |

### 8.3 方案 B · 自主构建

#### 8.3.1 定位

不接宿主，独立交付的单体或前后端分离应用。**宿主侧的一切基建需自建**：登录与 RBAC、菜单树、权限点、事件总线、迁移引擎、字典服务。

#### 8.3.2 两种技术形态（须与用户二选一）

| 形态 | 后端 | 前端 | 适用 |
|---|---|---|---|
| **B1 同栈自建** | ThinkPHP 8 + MySQL（版本不限，建议 8.0） | workdesktop-ai UMD + 静态页面 + 标准 API 驱动（与林枢同款，但无宿主） | 将来可能并入林工矩阵；团队是 PHP 背景；部署简单 |
| **B2 前后端分离** | 任选：ThinkPHP 8 / Node(NestJS) / Java(Spring Boot)，输出 REST + JWT | Vue 3 + Vite + Element Plus + Pinia + Vue Router；或 React 18 + AntD | 前端团队独立、交互重、需多端复用 |

#### 8.3.3 前端构建方式（B2 口径，B1 参照 §8.2.4 的 F-02~F-11 但自建宿主能力）

| 项 | B2 具体要求 |
|---|---|
| 脚手架 | `npm create vite@latest` + Vue 3 + TypeScript；禁手写 webpack 配置 |
| 目录 | `src/{api,views,components,stores,router,directives,utils,styles}`；页面按业务模块二级目录 |
| 路由 | `vue-router` 4，**动态路由**由后端返回菜单树生成；`meta.permission` 挂权限码，全局守卫拦截 |
| 权限 | `v-permission` 指令控显隐 + 守卫控路由；权限码唯一来源为后端 `permissions` 接口，前端不硬编码 |
| 请求层 | 单例 `axios` 实例 + 请求/响应拦截（token 注入、`{code,data,message}` 解包、401 跳登录、错误统一提示） |
| 状态 | Pinia，按模块分 store；用户信息与字典做持久化缓存并带版本号 |
| UI | Element Plus（按需引入）或 AntD；主题变量集中管理，禁散落硬编码色值 |
| 构建产物 | `npm run build` → `dist/`，history 模式需 nginx `try_files $uri $uri/ /index.html`；静态资源走 CDN 时配 `base` |
| 环境 | `.env.{development,staging,production}` 管理 `VITE_API_BASE_URL`；密钥不进前端产物 |
| 质量门禁 | ESLint + Prettier + `vue-tsc` 类型检查；CI 中构建失败即阻断 |
| 交付形态 | 若需与后端同机部署，产物放 `public/` 下由 Web 服务器托管 |

**B1 口径**：与 §8.2.4 的 F-02/F-03/F-04/F-09/F-10 相同（UMD 直引、`createReadyApp`、`wd-*` 组件、Headquarters、统一主题），但 F-07（菜单来自 `menus.php`）改为**自建菜单表 + 后端下发菜单树**，F-08（权限码来自 `permissions.php`）改为**自建权限表**，F-11 静态目录改 `public/static/`。

#### 8.3.4 开工包相应变化

| 文件 | 自主构建时的差异 |
|---|---|
| 1 | 删除「林枢接入声明」，改为「技术架构声明」（技术栈 / 部署形态 / 权限模型 / 事件机制）；弱依赖降级改为本系统内的开关配置 |
| 2 | 表前缀按用户约定（建议 `lg_{SHORT}_` 保持一致），并**自建**用户-角色-权限-菜单四张基础表与迁移记录表；数据库版本按实际选型 |
| 3 | T0 基建任务数增加：登录鉴权、RBAC、菜单树、事件总线（Redis Stream 或 MQ）、迁移引擎——**比方案 A 多约 20~30% 人日** |
| 4 | §0.2 前端技术基线按 §8.3.3 填；FE-00 为"工程脚手架 + 布局骨架 + 登录 + 动态路由 + 权限指令"；若 B2 则新增构建与部署任务 |
| 5 | 对账单 REL 任务改为通用发布流程（构建、镜像/产物、灰度、回滚），无包安装/卸载验证 |
| 6 | 「自建能力映射表」：全部点位标自建或跨系统协作，无宿主服务可复用——"避免重复开发"收益归零，此为方案 B 的隐性成本，登记入 §8.3.5 风险 |

#### 8.3.5 风险

| # | 风险 | 影响 | 建议 |
|---|---|---|---|
| 1 | 基建重复投入 | 每个产品各建一套 RBAC / 菜单 / 事件总线，八款产品重复八次 | 若客户明确要求独立部署，仍建议抽公共基建包 |
| 2 | 无法并入林工矩阵 | 后续若要组合售卖，需二次改造接入宿主 | 立项时即确认是否有组合诉求 |
| 3 | 前端工程化运维成本 | 需 Node 工具链、CI 缓存、产物版本管理 | 固化脚手架与 CI 模板，避免每项目一套 |

### 8.4 方案 C · 其他框架 / 客户既有宿主

#### 8.4.1 定位

接入非林枢的宿主（客户自有 ERP / 低代码平台 / 其他厂商 PaaS / DMP 后台），或按用户指定的第三方框架开发。

#### 8.4.2 立项前必须取得的宿主资料（缺一不可，缺项即登记 OI）

| # | 资料 | 用途 | 缺失后果 |
|---|---|---|---|
| 1 | 插件/扩展接入协议（包结构 + 清单字段 + 生命周期钩子） | 决定接入声明章节写法 | 无法设计安装与升级路径 |
| 2 | 权限模型（权限点定义方式、角色数据范围） | 文件 1 附录 E | 权限矩阵无法落地 |
| 3 | 菜单/导航注入方式 | 文件 4 页面清单与 FE-00 | 页面挂不上 |
| 4 | 事件/消息机制（主题命名、订阅方式、投递语义：至少一次 / 至多一次） | 文件 1 附录 C、文件 3 事件组 | 幂等设计缺乏依据 |
| 5 | 数据库与事务约束（版本、字符集、是否允许跨库、是否允许自建表） | 文件 2 硬规则 | 迁移方案不可执行 |
| 6 | 前端容器规范（是否 iframe、是否提供组件库、允许的构建产物形态） | 文件 4 §0.2 | 前端方案可能整段作废 |
| 7 | 鉴权（SSO / Token 传递 / 会话模型） | 文件 3 T0、文件 4 请求层 | 联调阻塞 |
| 8 | 宿主版本号与升级策略 | 版本约束与兼容任务 | 升级即破坏 |

#### 8.4.3 前端构建方式（按宿主形态三档）

| 宿主形态 | 构建方式 | 要点 |
|---|---|---|
| **提供组件库 + 服务端渲染容器**（如林枢这类） | 宿主组件库 UMD/ESM 直引 + 宿主模板渲染 | 严格按宿主的资源加载顺序与初始化入口；不自建路由与菜单 |
| **提供前端容器（iframe / 微前端 / qiankun）** | 独立 SPA，Vite 构建，产物对接宿主的挂载协议 | 需处理样式隔离、路由 base、通信（postMessage / props 注入）、鉴权透传 |
| **仅提供 API（宿主只管鉴权与菜单）** | 独立 SPA 或服务端渲染页面，构建方式同 §8.3.3 | 菜单与权限由宿主 API 下发；页面自建路由 |

**微前端补充要求**：子应用需导出宿主要求的生命周期（`bootstrap` / `mount` / `unmount`）；样式加命名空间前缀；不与宿主争用全局变量；独立部署时提供 fallback 直访模式。

#### 8.4.4 开工包相应变化

| 1 | 「接入声明」改为按宿主协议的「宿主接入说明」，并新增「宿主能力缺口表」（宿主不提供、需本包自建或绕行的能力） |
| 2 | 表前缀按宿主规则；若宿主禁止自建表，则列出受限项与替代方案（扩展字段 / 外部存储） |

#### 8.4.5 风险

宿主能力不确定是本方案最大风险。**处理原则：宿主资料未取得前，只产出文件 1 的骨架与本节 OI 清单，不产出文件 2~5**，避免整链返工。

### 8.5 三方案横向对比

| 维度 | A · 林枢功能包 | B · 自主构建 | C · 其他框架 / 既有宿主 |
|---|---|---|---|
| 宿主耦合 | 强（同进程加载） | 无 | 视宿主而定 |
| 后端基建工作量 | 低（复用宿主 RBAC/菜单/事件/迁移） | 高（全部自建，+20~30% 人日） | 中~高（取决于宿主能力缺口） |
| 前端构建 | workdesktop-ai UMD + 静态页面 + 标准 API 驱动，**无构建链** | B1 同上但自建宿主能力；B2 Vite 工程化 SPA | 按宿主容器形态（UMD / iframe / 微前端 / 仅 API） |
| 前端技术基线明确度 | 高（12 条硬性合规项） | 中（形态确定后明确） | 低（需先取宿主资料） |
| 可组合性（独立可卖 / 组合成拳） | 原生支持 | 不支持，需二次改造 | 取决于宿主生态 |
| 权限与菜单来源 | `permissions.php` / `menus.php` | 自建表 + 接口下发 | 宿主 API |
| 事件机制 | Redis Stream，主题 `lg.<short>.` | 自建（Redis Stream / MQ） | 宿主消息机制 |
| 数据库前缀 | `lg_{SHORT}_`（协议硬约束） | 用户约定，建议同规则 | 宿主规则 |
| 开工包差异量 | 接入声明六表 + T0 只做接入 + FE 合规 12 条 | 删接入声明 + T0 扩四类 + FE 基线自定 | 宿主接入说明 + 能力缺口表 + 适配任务组 |
| 典型场景 | 林工矩阵八款产品；客户可能组合购买 | 单客户私有化独立系统；明确不接矩阵 | 客户已有系统上扩展；集团平台内嵌 |
| 推荐度 | ★★★（默认） | ★★（有明确独立诉求时） | ★（宿主资料齐备时） |

### 8.6 框架确认的执行规约（AI 必须遵守）

#### 8.6.1 提问模板（一次性问清，不连环追问）
